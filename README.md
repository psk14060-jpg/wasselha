# وصّلها

نموذج عربي مستقل لتنظيم طلبات **ميني قيش** مع مطعم واحد ومندوب واحد. العميل ينشئ الطلب بنفسه من واجهة الويب، ويقبل المندوب المهمة، ثم يؤكد العميل الطلب قبل إتاحته للمطبخ.

هذه إعادة تنفيذ مستقلة لمسار العمل المتفق عليه، وليست نسخة مصدر مُصدّرة من Replit. لا يرسل التطبيق رسائل واتساب ولا ينفذ مدفوعات إلكترونية؛ وظيفته الحالية تجربة الطلب والتحصيل والعهدة. الأسعار والتوصيل بيانات إعداد تجريبية وليست منيو جديدًا معتمدًا.

## تشغيل سريع

يلزم **Node.js 24 أو أحدث**. لا توجد حزم تشغيل خارجية ولا حاجة إلى `npm install`.

```sh
npm run setup
npm start
```

افتح `http://127.0.0.1:3000`.

- صفحة العميل: `/#shop`.
- طلبات العميل: `/#orders`.
- لوحة المطعم: `/#restaurant`.
- لوحة المندوب: `/#courier`.

ينشئ الإعداد ملف `.env` محليًا بكلمتي مرور عشوائيتين مختلفتين. استخدم قيمة `RESTAURANT_PASSWORD` للمطعم و`COURIER_PASSWORD` للمندوب. لا يُستبدل ملف إعداد موجود. لا ترفع `.env` أو مجلد `data` إلى GitHub.

لكل دور جلسة منفصلة؛ يمكن فتح العميل والمطعم والمندوب في تبويبات على نفس المتصفح للتجربة، أو على أجهزة مختلفة عند تشغيل الخادم في بيئة مناسبة. العميل يرى طلباته من متصفحه الأصلي؛ استعادة الحساب أو التحقق برقم الجوال لم تُنفّذ بعد.

## مسار الطلب

| المرحلة | من ينفذها | الشرط |
| --- | --- | --- |
| إنشاء الطلب | العميل | المطعم يستقبل، وطاقة متاحة، وبيانات وأسعار صحيحة |
| قبول المهمة | المندوب | لا مهمة أو عهدة سابقة مفتوحة |
| تأكيد الطلب | العميل | المندوب قبل ولم تنته المهلة |
| بدء التجهيز | المطعم | العميل أكد |
| إعلان الجاهزية | المطعم | التجهيز بدأ |
| استلام الطلب | المندوب | جاهز؛ تأكيد استلام الجهاز لطلبات الشبكة |
| تسجيل التحصيل | المندوب | تسجيل المبلغ كاملًا ومرجع إيصال الشبكة عند الحاجة |
| التسليم | المندوب | التحصيل مسجل |
| تسوية التحصيل | المطعم | تأكيد استلام النقد أو مطابقة إيصال الشبكة |
| إغلاق العهدة | المندوب ثم المطعم | إعادة الجهاز ثم تأكيد المطعم استلامه |
| مكتمل | النظام | التسليم والتحصيل وعهدة الجهاز مغلقة |

التحصيل هنا **تسجيل يدوي لما حدث خارج التطبيق** وليس إثباتًا آليًا لوصول الأموال. الشبكة تعني جهاز المطعم الذي يحمله المندوب. فشل التحصيل يمنع التسليم، ويمكن تسجيل التعثر وإرجاع الطلب والعهدة إلى المطعم.

## السلوك الذي يحمي التشغيل

- حساب الأسعار من بيانات الخادم، بأعداد صحيحة من الهللات.
- معرّف للعملية يمنع تكرارها عند إعادة الإرسال، ويرفض استخدامه مع بيانات مختلفة.
- معاملات SQLite تمنع إسناد نفس الطلب مرتين وحجز الجهاز لطلبين.
- إخفاء رقم العميل والعنوان التفصيلي عن المندوب قبل قبول المهمة.
- صلاحيات العميل والمطعم والمندوب تتحقق في الخادم.
- انتهاء الطلب غير المقبول بعد 10 دقائق؛ مهلة تأكيد العميل 3 دقائق بعد قبول المندوب.
- إيقاف استقبال الطلبات أو تحديد حد متزامن بين 1 و20، مع استمرار معالجة الطلبات القائمة.
- تسليم الطلب لا يصفر النقد ولا يحرر جهاز الشبكة تلقائيًا.
- جلسات مخزنة بصماتها في قاعدة البيانات، وملفات تعريف ارتباط HttpOnly، والتحقق من CSRF، وحد لمحاولات الدخول.

## الاختبارات

```sh
npm run check
npm test
```

تشمل الاختبارات الأحد عشر مساري الكاش والشبكة، تكرار العمليات، قبولًا متزامنًا عبر HTTP، صلاحيات الأدوار، إخفاء بيانات العميل، انتهاء المهلة، طاقة المطعم، تعثر التسليم، استمرار البيانات بعد إعادة التشغيل، وتشغيل الخادم كعملية مستقلة وخدمة ملفات الواجهة. يوجد سير GitHub Actions لتشغيلها عند الدفع وطلبات الدمج.

لا تغني اختبارات الخادم عن تجربة الواجهات على الجوال. راجع [قائمة تجربة التشغيل](docs/acceptance.md) قبل استخدام النسخة خارج الاختبار.

## البيانات والتشغيل

الواجهة HTML/CSS/JavaScript، والخادم Node.js، وقاعدة البيانات SQLite محفوظة في `data/wasselha.sqlite`. لا تُحفظ الطلبات في localStorage. الدليل التجريبي يحتوي مطعمًا واحدًا وأربعة أصناف وجهاز شبكة واحدًا. التحميل الأول لا ينشئ طلبات تلقائية.

هذه النسخة مصممة **لخادم واحد وقرص دائم واحد**. لم تُختبر كمنصة موزعة أو تحت ضغط إنتاجي. لا تشغّل نسخًا متعددة على أقراص منفصلة وتتوقع مشاركة الطلبات. عند التوسع يلزم نقل مخطط البيانات إلى قاعدة مشتركة وإضافة تشغيل ومراقبة ونسخ احتياطية مناسبة.

خيارات البيئة موضحة في `.env.example`. الاستماع الافتراضي محلي فقط. للاستضافة استخدم HTTPS وكلمتي مرور خاصتين و`COOKIE_SECURE=true` مع تخزين دائم. لا تضع الخادم الحالي على الإنترنت باعتباره جاهزًا لطلبات عملاء حقيقية.

يوجد Dockerfile لتسهيل النقل. يجب تمرير كلمات المرور كأسرار تشغيل وربط مجلد دائم عند `/app/data`؛ لا تُضمّن الأسرار في الصورة. المسار `/health` يعرض جاهزية خدمة HTTP فقط.

## ما بقي قبل تجربة حقيقية

- اعتماد الأصناف والأسعار ورسوم التوصيل ومنطقة الخدمة.
- ربط قناة العميل الحقيقية أو اعتماد رابط طلب العميل وتحديد طريقة إرساله.
- ربط WhatsApp Business الرسمي إذا أريد استقبال الرسائل وإرسالها آليًا؛ المحاكاة الحالية ليست ربطًا لواتساب.
- التحقق من رقم العميل واستعادة طلباته عبر الأجهزة، ومراجعة سياسات الاحتفاظ بالبيانات.
- التحقق اليدوي من الواجهة على أجهزة المطعم والمندوب والعميل.
- إعداد HTTPS والنسخ الاحتياطي والمراقبة واستعادة الخدمة.

وجود الكود في GitHub وحده لا ينشئ موقعًا مستضافًا. البناء والاختبارات منفصلان عن النشر والربط الفعلي بواتساب.
