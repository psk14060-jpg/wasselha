# وصّلها

منصة عربية لربط مطاعم مستقلة بمناديب توصيل مستقلين، بديلًا عن عمولة تطبيقات التوصيل (20–30٪) برسم ثابت: اشتراك شهري + رسم صغير لكل طلب. هذه هي **المرحلة الأولى** من خارطة الطريق: كل مطعم يسجّل حسابه بنفسه، وكل مندوب حساب مستقل يعمل عبر أي مطعم منضم. لا ربط رسمي بواتساب بزنس أو ذكاء اصطناعي أو خرائط قوقل بعد (تلك مرحلة لاحقة) — فقط زر يفتح واتساب برسالة جاهزة يرسلها العميل يدويًا لرقم المطعم. لا بوابة دفع للمنصة (التحصيل نقدًا للمندوب، أو رابط دفع يشاركه المطعم مباشرة لحسابه الخاص).

هذه إعادة تنفيذ مستقلة، وليست نسخة مصدر مُصدّرة من Replit. الأسعار ورسوم التوصيل بيانات إعداد تجريبية لكل مطعم يضبطها بنفسه.

كل مطعم يضيف رقم واتساب عادي من إعداداته (بدون أي حساب Meta Developer أو WhatsApp Business API)؛ عند إنشاء الطلب يظهر للعميل زر يفتح واتساب برسالة جاهزة بتفاصيل الطلب لإرسالها لرقم المطعم مباشرة — نفس أسلوب مواقع المنيو الرقمي المنتشرة (مثل منيو سهل وبقدونس)، كطبقة إشعار فورية فوق نظام التتبع الحالي، لا بديلًا عنه.

## تشغيل سريع

يلزم **Node.js 24 أو أحدث**. لا توجد حزم تشغيل خارجية ولا حاجة إلى `npm install`.

```sh
npm run setup
npm start
```

افتح `http://127.0.0.1:3000`.

- دليل المطاعم للعميل: `/#shop`.
- منيو مطعم محدد: `/#shop/<معرّف المطعم>`.
- طلبات العميل: `/#orders`.
- تسجيل مطعم جديد: `/#restaurant/signup` · دخول مطعم: `/#restaurant`.
- تسجيل مندوب جديد: `/#courier/signup` · دخول مندوب: `/#courier`.

كل مطعم ومندوب يُنشئ حسابه بكلمة مرور خاصة (12 حرفًا على الأقل) من الواجهة مباشرة — لا كلمات مرور مُعدّة مسبقًا في `.env`. لكل دور جلسة منفصلة؛ يمكن فتح العميل والمطعم والمندوب في تبويبات على نفس المتصفح للتجربة. العميل يرى طلباته من متصفحه الأصلي؛ استعادة الحساب أو التحقق برقم الجوال لم تُنفّذ بعد.

## مسار الطلب

| المرحلة | من ينفذها | الشرط |
| --- | --- | --- |
| إنشاء الطلب | العميل | المطعم يستقبل، وطاقة متاحة، وبيانات وأسعار صحيحة |
| قبول المهمة | المندوب | لا مهمة مفتوحة له في أي مطعم آخر |
| تأكيد الطلب | العميل | المندوب قبل ولم تنته المهلة |
| بدء التجهيز | المطعم | العميل أكد |
| إعلان الجاهزية | المطعم | التجهيز بدأ |
| استلام الطلب | المندوب | جاهز |
| تسجيل التحصيل | المندوب | تحصيل كامل المبلغ نقدًا من العميل |
| التسليم | المندوب | التحصيل مسجل |
| تسوية المطعم | المطعم | تأكيد استلام سعر الأصناف من المندوب (المبلغ ناقص رسوم توصيله، لأن المندوب يحتفظ بها فورًا) |
| مكتمل | النظام | التسليم والتسوية تمّا |

التحصيل هنا **تسجيل يدوي لما حدث خارج التطبيق**: المندوب يستلم كامل المبلغ نقدًا من العميل، يحتفظ برسوم توصيله فورًا، ويسلّم الباقي للمطعم عند التسوية. فشل التحصيل يمنع التسليم، ويمكن تسجيل التعثر وإرجاع الطلب للمطعم دون تحصيل.

## السلوك الذي يحمي التشغيل

- حساب الأسعار من بيانات الخادم، بأعداد صحيحة من الهللات.
- معرّف للعملية يمنع تكرارها عند إعادة الإرسال، ويرفض استخدامه مع بيانات مختلفة.
- معاملات SQLite تمنع إسناد نفس الطلب مرتين، وتمنع مندوبًا من قبول مهمة ثانية قبل إغلاق الأولى — عبر أي مطعم.
- إخفاء رقم العميل والعنوان التفصيلي عن المندوب قبل قبول المهمة.
- صلاحيات العميل والمطعم والمندوب تتحقق في الخادم، بما فيها تحقق ملكية المطعم لطلباته تحديدًا.
- انتهاء الطلب غير المقبول بعد 10 دقائق؛ مهلة تأكيد العميل 3 دقائق بعد قبول المندوب.
- كل مطعم يوقف استقبال الطلبات أو يحدد حده المتزامن بين 1 و20 بشكل مستقل، مع استمرار معالجة طلباته القائمة.
- تسليم الطلب لا يصفر التحصيل تلقائيًا؛ تسوية المطعم خطوة منفصلة ومقفلة على مبلغ محدد.
- لا جهاز نقاط بيع تتم مشاركته أو إرجاعه — أُزيل هذا التصميم لأنه كان يمنع مندوبًا مستقلًا من قبول مهمة جديدة لين يرجع لمطعم سابق، ويفترض جهازًا واحدًا فقط لكل مطعم.
- جلسات مخزنة بصماتها في قاعدة البيانات، وملفات تعريف ارتباط HttpOnly، والتحقق من CSRF (على الطلبات المُغيّرة للبيانات جميعها)، وحد لمحاولات الدخول والتسجيل.

## الفوترة

رسم المنصة **99 ريال اشتراك شهري + 2 ريال عن كل طلب مكتمل** لكل مطعم، يُحسب من مسار `GET /api/restaurant/billing` كفاتورة دورية منفصلة عن أي معاملة — لا خصمًا تلقائيًا من التحصيل، ولا يمر بأي بوابة دفع للمنصة. التحصيل الفعلي حاليًا يدوي (تحويل بنكي مثلًا) خارج هذه النسخة.

## الاختبارات

```sh
npm run check
npm test
```

تشمل الاختبارات: تسعير الخادم وتكرار العمليات، رحلة الطلب الكاملة نقدًا حتى التسوية والإغلاق، مندوبًا مستقلًا يعمل عبر أكثر من مطعم بمهمة واحدة نشطة فقط، عزل الطاقة والإيقاف بين المطاعم، انتهاء المهلة، إخفاء بيانات العميل عن غير المعنيين، تعثر التسليم، حساب الفوترة الشهرية، استمرار البيانات بعد إعادة التشغيل، وتسجيل مطعم ومندوب فعليًا عبر HTTP مع حماية CSRF وقبولًا متزامنًا عبر الشبكة. يوجد سير GitHub Actions لتشغيلها عند الدفع وطلبات الدمج.

لا تغني اختبارات الخادم عن تجربة الواجهات على الجوال. راجع [قائمة تجربة التشغيل](docs/acceptance.md) قبل استخدام النسخة خارج الاختبار.

## البيانات والتشغيل

الواجهة HTML/CSS/JavaScript، والخادم Node.js، وقاعدة البيانات SQLite محفوظة في `data/wasselha.sqlite` — تدعم عدة مطاعم ومناديب في قاعدة واحدة. لا تُحفظ الطلبات في localStorage. التحميل الأول لا ينشئ مطاعم أو طلبات تلقائية؛ كل مطعم يسجّل نفسه ويضيف منيوه بنفسه من لوحته.

هذه النسخة مصممة **لخادم واحد وقرص دائم واحد**. لم تُختبر كمنصة موزعة أو تحت ضغط إنتاجي. عند التوسع الكبير (المرحلتان 2 و3 من خارطة الطريق) يلزم نقل مخطط البيانات إلى قاعدة مشتركة وإضافة تشغيل ومراقبة ونسخ احتياطية مناسبة.

خيارات البيئة موضحة في `.env.example`. الاستماع الافتراضي محلي فقط. للاستضافة استخدم HTTPS و`COOKIE_SECURE=true` مع تخزين دائم. لا تضع الخادم الحالي على الإنترنت باعتباره جاهزًا لعملاء حقيقيين.

يوجد Dockerfile لتسهيل النقل. يجب ربط مجلد دائم عند `/app/data`. المسار `/health` يعرض جاهزية خدمة HTTP فقط.

## ما بقي قبل تجربة حقيقية

- **المرحلة 2 من خارطة الطريق**: ربط واتساب بزنس الرسمي وذكاء اصطناعي لقراءة الطلبات، سوق آلي للمناديب، وتكامل خرائط قوقل لفحص وقت الوصول قبل تثبيت المندوب.
- التحقق من رقم الجوال واستعادة الحسابات عبر الأجهزة لكل من العميل والمطعم والمندوب.
- تحصيل فعلي لفاتورة المنصة الشهرية (حاليًا رقم محسوب فقط، بلا تكامل دفع أو تذكير آلي).
- تحديد نطاق التوصيل الجغرافي وربطه بمعادلة رسوم التوصيل بدل رقم ثابت يضبطه كل مطعم يدويًا.
- التحقق اليدوي من الواجهة على أجهزة المطعم والمندوب والعميل الحقيقية.
- إعداد HTTPS والنسخ الاحتياطي والمراقبة واستعادة الخدمة قبل أي استضافة عامة.

وجود الكود في GitHub وحده لا ينشئ منصة مستضافة. البناء والاختبارات منفصلان عن النشر والربط الفعلي بواتساب وخرائط قوقل.
